# Рекомендации на витрине + надёжная привязка по username

Дата: 2026-06-08
Статус: на ревью

## Контекст

Витрина студентов курса показывает 68 опубликованных профилей. Движок рекомендаций
(месячный LLM-батч, `packages/parser/src/recommend.ts`) уже сгенерировал 316 связок
«с кем полезно познакомиться» на 66 студентов, с обоснованием reason для каждой.

Две проблемы мешают этому работать как нетворкинг-инструменту:

1. **Доставка спрятана.** Рекомендации показываются на отдельной странице
   `/recommendations`, на которую ведёт баннер. Заказчик хочет, чтобы рекомендации
   жили **на главном экране витрины**: кнопка «Ваши рекомендации» → попап со списком
   рекомендованных профилей. Отдельной страницы быть не должно.

2. **Вход почти ни у кого не привязывается к своей карточке.** Привязано 3 из 68.
   При логине `getOrAttachStudent` (`apps/bot/src/students.ts`) ищет профиль по
   `telegram_user_id`, затем по имени (`import_key`), иначе создаёт новый пустой.
   Матчинга по `@username` нет. Если имя в Telegram ≠ имя из чата — студент логинится
   в пустую карточку без рекомендаций. При этом `@username` есть у всех 68, дублей
   username — 0. Матчинг по username привяжет 66 непривязанных к их настоящим карточкам.

Без правки #2 кнопка из #1 будет видна почти никому — поэтому делаем обе части.

## Цель

Залогиненный студент на главном экране витрины видит кнопку «Ваши рекомендации · N»,
по клику открывается попап с профилями людей, с которыми ему полезно познакомиться,
и обоснованием для каждого. Вход остаётся прежним (deep-link через бота).

## Не входит в scope

- Telegram Login Widget (решено оставить текущий deep-link вход).
- Массовый импорт аватаров и чистка грязной страны в карточке («Москва, Аргентина») —
  отдельные задачи.
- Изменение самого алгоритма подбора рекомендаций.

## Компонент 1 — Рекомендации как кнопка + попап на витрине

### Данные (server)

`apps/web/app/students/page.tsx` уже вычисляет `myId` и `recCount`. Заменяем подсчёт
`recCount` на загрузку самих рекомендаций:

- Запрос к `tbl('recommendations')`: `recommended_id, reason, rank` где `student_id = myId`,
  сортировка по `rank asc`.
- Сшиваем `recommended_id` с уже загруженным массивом `items` (по `id`). Рекомендованные,
  которых нет среди опубликованных, отбрасываем.
- Передаём в `Directory` новый проп `recommendations: { item: DirItem; reason: string | null }[]`
  вместо `recCount`.

### UI (client, `apps/web/app/students/directory.tsx`)

- Проп `recCount` заменяется на `recommendations`.
- Над списком участников (где сейчас `RecBanner`) — кнопка **«Ваши рекомендации · N»**.
  Рендерится только если `recommendations.length > 0`. Стиль — акцентная кнопка из
  существующей палитры (без теней/градиентов).
- Клик → состояние `recsOpen`, открывается модалка тем же паттерном, что текущий
  `Modal` (оверлей `bg-black/35 backdrop-blur`, карточка по центру, закрытие по фону/крестику).
- Содержимое модалки — список рекомендаций. Каждый пункт:
  - аватар + имя + ниша/город (переиспользуем `Avatar` и `statusText` из directory.tsx);
  - блок reason («почему стоит познакомиться») в `bg-accent-light`;
  - кнопки «Написать» (`https://t.me/<telegram>`) и «Открыть профиль» (ведёт на
    `/students/<slug>` — отдельную модалку поверх не открываем, чтобы не плодить слои).
- `RecBanner` и `recPlural` удаляются из directory.tsx.

### Удаления

- Файл `apps/web/app/recommendations/page.tsx` — удалить.
- Все ссылки на `/recommendations` (баннер, тексты в боте, если ведут на страницу) —
  заменить или убрать. Текст пустого состояния про «заполните профиль» переносится в
  попап (если у студента 0 рекомендаций — кнопка просто не показывается).

## Компонент 2 — Привязка по `@username` при входе

### Файл: `apps/bot/src/students.ts`, функция `getOrAttachStudent`

Новый порядок поиска профиля:

1. по `telegram_user_id` (как сейчас);
2. **по `telegram_username`** — точное совпадение без учёта регистра, только среди
   непривязанных (`telegram_user_id is null`), в рамках текущего `cohort`, и только если
   совпадение ровно одно (иначе пропуск — как в `reconcileFromChat`). При совпадении —
   проставляем `telegram_user_id` и обновляем `telegram_username`, возвращаем профиль;
3. по имени `import_key` (как сейчас);
4. иначе создать новый (как сейчас).

Эта функция вызывается и в боте-кабинете, и в deep-link флоу веб-логина (`bot.start`
дёргает её перед записью `student_id` в `web_auth_tokens`). Одна правка чинит оба пути.

### Безопасность матчинга

- Сравнение username — `lower()` с обеих сторон; Telegram username регистронезависим.
- Привязка только при единственном непривязанном совпадении (дублей username в данных нет,
  но защита на будущее).
- Не трогаем `is_published`: импортированные карточки уже опубликованы, согласие не
  переспрашиваем; новые остаются `is_published=false` до `/agree`.

## Поток (итог)

1. Студент открывает сайт → «Войти через Telegram» → бот → «Запустить» → назад на сайт.
2. На входе бот привязывает его к настоящей карточке по `@username`.
3. На витрине появляется кнопка «Ваши рекомендации · N».
4. Клик → попап с профилями рекомендованных + «почему» + «Написать».

## Тестирование

- **Unit (бот):** рядом с `apps/bot/test/reconcile-profiles.test.ts` — тест на
  `getOrAttachStudent`: (а) привязка по username к непривязанному профилю; (б) пропуск
  при неоднозначности; (в) приоритет `telegram_user_id` над username; (г) падение в
  создание нового, если ни id, ни username, ни имя не совпали.
- **Ручная проверка (web):** залогиниться, увидеть кнопку с верным N, открыть попап,
  проверить reason и кнопки «Написать»/«Открыть профиль»; у студента без рекомендаций
  кнопки нет.
- Прогон `npx tsc --noEmit` для web и `npm test` для бота.

## Операционно

- Деплой бота — отдельный сервис; правка `students.ts` требует передеплоя бота.
